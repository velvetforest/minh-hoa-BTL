BM25: score a chunk by the query words it contains

BM25 (Best Match 25) is a ranking function from classic information retrieval. It needs no training: it only counts words. We use the Lucene variant through the bm25s library.

Formula

score(q,d)= ∑t∈q IDF(t)· f(t,d)·(k1+1) f(t,d)+k1·(1−b+b·|d|avgdl)
IDF(t)=ln(1+N−n(t)+0.5n(t)+0.5)
q, d
the query and one chunk (both as word lists)
f(t, d)
how many times word t appears in chunk d
|d|, avgdl
length of this chunk, average chunk length (74 words in our corpus)
N, n(t)
number of chunks (2,576), number of chunks containing t
k₁ = 1.2
saturation: the 10th repeat of a word adds far less than the 1st
b = 0.75
length penalty: long chunks do not win just by having more words

Why Vietnamese needs word segmentation

Vietnamese separates syllables, not words. Splitting by spaces makes "doanh" match "doanh thu" (revenue).

Split by spaces

Data flow through the files

Reading order

  1. __init__.py exports BM25Retriever, tokenize_vi, RetrievalUnavailableError.
  2. tokenizer.py turns text into tokens. Used by both build and query, so they always match.
  3. bm25.py builds, saves, loads and queries the index.
  4. __main__.py is the command line: build and query.
  5. tests/test_bm25_retrieval.py: 18 tests, 5-chunk fake corpus, runs in < 1 s.

Key decisions

  • Legal refs cut out before underthesea. Otherwise 59/2020/QH14 becomes two tokens. This fix lifted Recall@20.
  • Filter at build time, not at query time: only con_hieu_luc and het_hieu_luc_mot_phan are indexed.
  • Manifest check on load: an index built from other chunks refuses to run.
  • Output = contract: tests validate it with retrieval_output.schema.json.

Alone, underthesea breaks the article number and the law number apart, so a question about "Điều 206" also matches every chunk with the number 206 anywhere. An earlier version used a placeholder word instead of cutting, and underthesea glued it to the previous word (luật_xlegalxax). A unit test caught it.

The core of T4 + T5

spans = []                       # (start, end, token)
for pattern, render in LEGAL_PATTERNS:
    for m in pattern.finditer(text):
        if not overlapping(m, spans):
            spans.append((m.start(), m.end(), render(m)))
tokens, pos = [], 0
for start, end, legal in sorted(spans):
    tokens += segment(text[pos:start])   # underthesea
    tokens.append(legal)                 # kept whole
    pos = end
tokens += segment(text[pos:])
Patterns: document numbers \d+/\d{4}/… and điều | khoản | điểm | chương + number. "điều kiện", "điều lệ" are not caught (tested).

5 drop score 0A chunk sharing no word is never returned

Dense: find chunks with the same meaning, even with different words

This page explains the idea behind dense-retrieval-proposal.md. The module is now built and tested (pages 7 and 8, PR #26), but it has not yet run with the real model, so no Recall numbers yet.

Definition

An embedding model turns any text into a vector of 1,024 numbers. Texts with similar meaning get vectors that point in similar directions.

v=Embed(text)∈ℝ1024
sim(q,d)=cosθ=q·d‖q‖‖d‖

1 means same direction, 0 means unrelated. We L2-normalise every vector, so cosine becomes a plain dot product q·d. No word segmentation and no shared words are needed.

Intuition (illustration, not measured)

How it is used

  • Offline: embed context_header + "\n" + content of every chunk, store vector + metadata in Qdrant (collection legal_chunks, cosine distance).
  • Online: embed the question with the same model, ask Qdrant for the top-k nearest vectors, return retrieval_method = "dense".
  • Model: AITeamVN/Vietnamese_Embedding (BGE-M3 base). Switch to vnlegal-lal or vietlegal-e5 if Recall@20 is ≥ 3 points higher.
For the benchmark: torch + model ≈ 3–4 GB, Qdrant via Docker. Tests need none.

Hybrid: Reciprocal Rank Fusion (VLRA-27)

RRF(d)=∑r∈{BM25,Dense}1k+rankr(d)

Take the top 100 of each branch and add ranks, not raw scores (BM25 and cosine use different scales). k = 60. A chunk ranked high in both branches rises to the top. Returns retrieval_method = "hybrid_rrf".

Page 7 · How Dense was implemented · PR #26

From chunks.jsonl to Qdrant to Team 2

Same package team1_data/retrieval/, branch feature/team1/dense-retrieval (stacked on PR #25). Same API shape as BM25, so Hybrid can call both the same way.

Data flow through the files

Reading order

  1. __init__.py now imports lazily: BM25 needs only bm25s, Dense needs only qdrant-client.
  2. common.py (new) holds what both branches share: input checks, legal_status filter, output rows. bm25.py now uses it, behaviour unchanged.
  3. embedding.py turns text into vectors with sentence-transformers.
  4. dense.py builds the Qdrant collection, saves, connects and queries.
  5. __main__.py gains dense-build and dense-query.
  6. tests/test_dense_retrieval.py: 22 tests, runs in ~2 s.

Key decisions

  • Model pinned in the manifest (name, revision, dim). Another model or revision refuses to connect: vectors from two models are not comparable.
  • New version = new collection; rebuilding an existing one is refused. The alias moves only after the point count checks out.
  • Filter twice: at build time and again in the Qdrant query.
  • Any Qdrant error → RetrievalUnavailableError, never a silent [].
